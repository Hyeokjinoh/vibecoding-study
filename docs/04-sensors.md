# 4. Sensors — 행동한 뒤에 되돌린다

> **검증일**: 2026-08-28 · **Claude Code**: v2.1.247

## 한 줄 요약

센서(Sensors)는 에이전트가 만든 결과를 관찰해서 **에이전트 자신이 읽을 수 있는 신호**로 되돌려 주는 통제입니다. 핵심 조건은 딱 하나예요 — 사람이 눈으로 보는 검사는 센서가 아닙니다. **에이전트가 스스로 돌릴 수 있어야** 루프가 닫힙니다.

---

## 4.1 센서란 무엇인가

3장의 가이드는 행동 **전**에 방향을 줬습니다. 센서는 행동 **후**에 결과를 재서 신호를 돌려주고요. 제어공학의 용어를 빌리면 앞엣것이 피드포워드, 뒤엣것이 피드백입니다.

센서가 없으면 어떻게 될까요?

`CLAUDE.md` 에 "테스트를 먼저 돌려라"라고 적어 뒀다고 해봅시다. 그런데 진짜 돌렸는지 확인할 방법이 없다면? 그 규칙은 **지켜졌는지 아무도 모르는 상태**로 남습니다. 적어 두기만 한 규칙은 규칙이 아니라 희망사항이에요.

더 실무적인 문제도 있습니다. 센서가 없으면 "다 된 것 같다"가 유일한 종료 신호가 됩니다. 그러면 **사람이 검증 루프 그 자체**가 되죠. 에이전트를 붙여 놓고 사람이 결과를 하나하나 확인해야 한다면, 속도를 얻은 게 아니라 일의 종류만 바뀐 겁니다.

### 결정적 센서와 추론적 센서

센서는 두 종류입니다. 이 구분이 이 장의 뼈대예요.

| | **결정적 (Computational)** | **추론적 (Inferential)** |
|---|---|---|
| 실행 주체 | CPU | 모델(LLM) |
| 재현성 | 같은 입력 → 항상 같은 판정 | 매번 조금씩 다릅니다 |
| 속도·비용 | 밀리초~초, 거의 공짜 | 초~분, 토큰 비용 |
| 볼 수 있는 것 | 규칙으로 표현 가능한 것 | 의미·의도·"이거 과설계 아닌가" |
| 예 | 테스트, 린터, 타입 체커, 스키마 검증 | 리뷰 서브에이전트, LLM 이 읽도록 쓴 린트 메시지 |

결정적 센서는 싸고 믿을 만합니다. 그래서 **매 편집, 매 커밋마다 돌릴 수 있고요.** 하네스의 하중을 실제로 견디는 부분이 여기입니다. 하네스를 새로 짤 때 여기부터 채우는 이유죠.

추론적 센서는 규칙으로 표현할 수 없는 것을 봅니다. "이 테스트가 의미 있는 테스트인가", "요구사항 중 빠진 게 있나" 같은 판정은 계산으로 안 나오거든요. 대신 느리고 흔들립니다. 그러니 **매 키 입력이 아니라 파이프라인에 예산을 잡아** 배치하세요.

> 💭 **필자 견해**
>
> 추론적 센서를 처음 붙일 때 흔히 하는 실수가 있습니다. 리뷰 에이전트에게 "문제를 찾아 줘"라고만 시키는 거예요. 문제를 찾으라고 하면 **항상 찾아옵니다.** 없어도 만들어 오고요. 범위를 "정확성과 명시된 요구사항"으로 좁히지 않으면 과설계 제안만 잔뜩 쌓입니다.

## 4.2 에이전트가 스스로 돌릴 수 있어야 센서다

이 절이 이 장에서 가장 중요합니다. 검사가 아무리 정교해도, 사람이 화면을 보고 판단해야 한다면 그건 센서가 아니에요. **에이전트의 루프 밖에 있는 검사**니까요.

기준은 이렇게 잡습니다.

1. 에이전트가 **명령 하나로 실행**할 수 있는가
2. 결과가 **종료 코드나 텍스트**로 나오는가
3. 실패했을 때 **무엇을 고쳐야 하는지** 출력에 들어 있는가

셋 다 예라면 센서입니다. 하나라도 아니면 사람이 루프 안에 끼어 있는 거예요.

| 센서가 아니다 | 센서다 |
|---|---|
| "브라우저에서 열어 보고 확인" | 스크린샷을 기준 이미지와 diff 하는 스크립트 |
| "코드 리뷰에서 눈으로 확인" | 리뷰 서브에이전트가 diff 를 읽고 지적 목록을 반환 |
| "빌드가 잘 되는지 지켜본다" | 종료 코드를 반환하는 빌드 명령 |
| "성능이 괜찮은지 체감한다" | p95 지연이 임계값을 넘으면 실패하는 부하 테스트 |

오른쪽 항목들의 공통점이 보이시나요? **판정이 자동으로 나온다**는 것입니다. 왼쪽에서 오른쪽으로 옮기는 작업이 하네스 엔지니어링의 상당 부분을 차지해요.

따라오는 원칙이 하나 더 있습니다. 에이전트에게 "됐습니다"를 받지 마시고 **증거를 요구**하세요. 실행한 명령과 그 출력을 함께 내놓게 하면, 검증했다고 주장만 하는 경우를 걸러낼 수 있습니다. Anthropic 의 실무 문서는 이 태도를 짧게 요약합니다 — "If you can't verify it, don't ship it."(<https://code.claude.com/docs/en/best-practices>)

## 4.3 센서 출력은 LLM 이 읽을 것을 전제로 쓴다

센서의 출력은 사람이 아니라 **모델이 읽습니다.** 그러면 좋은 출력의 기준도 달라지죠. 짧아야 하고, 기계가 파싱할 수 있어야 하고, 무엇을 고칠지가 들어 있어야 합니다.

400줄짜리 스택 트레이스는 나쁜 센서 출력이에요. 컨텍스트를 잔뜩 먹고, 정작 신호는 그 안에 묻히니까요. 컨텍스트가 유한한 예산이라는 점을 떠올려 보면 이건 그냥 낭비가 아닙니다. **다른 규칙의 준수율까지 떨어뜨리는 비용**이에요.

**나쁜 예**

```text
Traceback (most recent call last):
  File "/usr/lib/python3.12/site-packages/_pytest/runner.py", line 341, in from_call
    result: Optional[TResult] = func()
  ... (380줄 생략) ...
AssertionError
```

무엇이 왜 틀렸는지가 없습니다. 에이전트는 이걸 받고 추측을 시작해요.

**좋은 예**

```text
FAILED tests/test_auth.py::test_refresh - AssertionError: expected 401, got 500
```

한 줄에 파일, 테스트 이름, 기대값, 실제값이 모두 들어 있죠. 에이전트는 이걸 파싱해서 곧장 해당 파일로 갑니다. 사람의 개입 없이 고치고 다시 돌리고요.

추론적 센서에서는 한 걸음 더 나갈 수 있습니다. 린트 메시지를 **모델에게 하는 지시문처럼** 쓰는 거예요.

```text
raw SQL 대신 repository.findBy... 를 쓸 것. 배경은 src/db/README.md 참고.
```

"금지된 패턴입니다" 로 끝내지 마세요. 대신 무엇을 쓸지와 근거가 어디 있는지까지 담습니다. 센서가 곧 가이드 역할까지 겸하게 되는 지점입니다.

> 💭 **필자 견해**
>
> 도구의 출력 형식을 설계하는 일을 사람 UI 만큼 진지하게 다루는 팀은 드뭅니다. 그런데 에이전트를 붙이는 순간 **에러 메시지가 곧 인터페이스**가 돼요. 나쁜 에러 메시지는 이제 불친절함의 문제가 아니라 **고장 난 센서**입니다.

## 4.4 강제 단계 사다리

같은 검사라도 어디에 붙이느냐에 따라 강제력이 달라집니다. 아래로 갈수록 세져요.

```mermaid
flowchart TB
    L1["1단계 · 프롬프트 안 지시<br/>'테스트를 돌리고 통과할 때까지 고쳐'"]
    L2["2단계 · 훅 (Hook)<br/>정해진 시점에 스크립트가 무조건 실행"]
    L3["3단계 · 검증 서브에이전트<br/>새 컨텍스트로 결과만 보고 판정"]
    L1 -->|"강제력 ↑<br/>비용 ↑"| L2
    L2 -->|"강제력 ↑<br/>비용 ↑"| L3
    N1["모델이 잊으면 끝<br/>추론적"]
    N2["모델과 무관하게 실행<br/>exit 2 로 차단 가능<br/>결정적"]
    N3["만든 주체와 검사 주체 분리<br/>의미까지 판정<br/>추론적"]
    L1 -.- N1
    L2 -.- N2
    L3 -.- N3
```

**1단계 — 프롬프트 안 지시.** 가장 싸고 가장 약합니다. 짧은 작업에는 충분하지만, 세션이 길어지면 조용히 잊혀요.

**2단계 — 훅.** 정해진 생애주기 시점에서 셸 명령이 실행됩니다. 모델이 협조하든 안 하든 실행돼요. 그래서 **매번 반드시 일어나야 하는 일**은 여기에 둡니다. 3장 마지막에 남겨 둔 "사라지지 않은 항목"들이 이 자리로 옵니다.

**3단계 — 검증 서브에이전트.** 새 컨텍스트에서 결과만 읽고 판정합니다. 만든 주체와 검사하는 주체를 분리하는 maker/checker 구조예요. 자기가 방금 쓴 코드에 대해서는 누구도(모델도) 좋은 심사위원이 아니라는 전제가 깔려 있습니다.

세 단계는 배타적이지 않습니다. 실제 하네스는 셋을 겹쳐 써요. 이 저장소도 그렇습니다 — `.claude/commands/verify.md` 는 결정적 스크립트와 추론적 검증 에이전트를 **둘 다** 돌리고 결과를 합쳐서 보고합니다.

## 4.5 Hooks 상세

훅(hook)은 Claude Code 가 정해진 생애주기 시점에서 실행하는 셸 명령입니다(HTTP 호출, MCP 도구 호출, 프롬프트, 에이전트 형태도 가능하고요). 핵심은 **모델이 무엇을 결정하든 상관없이 실행된다**는 점이에요.

### 이벤트 종류

이벤트는 성격별로 묶어서 외우는 편이 쉽습니다.

| 묶음 | 이벤트 |
|---|---|
| 세션 | `SessionStart`, `SessionEnd`, `Setup` |
| 턴 | `UserPromptSubmit`, `UserPromptExpansion`, `Stop`, `StopFailure` |
| 도구 | `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `PermissionRequest`, `PermissionDenied`, `PostToolBatch` |
| 그 밖 | `Notification`, `SubagentStart`, `SubagentStop`, `TaskCreated`, `TaskCompleted`, `FileChanged`, `PreCompact`, `PostCompact` 등 |

센서 관점에서 자주 쓰는 건 넷입니다. **`PostToolUse`** 는 편집 직후 검사를 붙이는 자리, **`PreToolUse`** 는 위험한 동작을 미리 막는 자리, **`Stop`** 은 검사가 통과할 때까지 턴을 끝내지 못하게 하는 자리, **`SessionStart`** 는 세션 시작 시 필요한 맥락을 주입하는 자리예요.

### 설정 모양

훅은 아무 설정 파일의 `hooks` 키 아래에 두시면 됩니다(스킬·서브에이전트 frontmatter 나 플러그인의 `hooks/hooks.json` 도 가능해요). `.claude/settings.json` 기준으로는 이렇게 생겼습니다.

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/format.sh"
          }
        ]
      }
    ]
  }
}
```

구조는 `이벤트 이름 → 매처 그룹 배열 → 그 안의 훅 배열`입니다. `${CLAUDE_PROJECT_DIR}` 같은 경로 자리표시자를 쓰면 어느 디렉터리에서 실행하든 경로가 맞아요. 명령·HTTP·MCP 도구 훅의 기본 타임아웃은 600초입니다.

전부 끄고 싶으시면 `"disableAllHooks": true` 를 설정에 넣으세요. 남의 저장소를 처음 열어 볼 때 알아 두면 좋은 스위치입니다.

### matcher 문법

- 정확한 이름: `Bash`
- 여러 개: `Edit|Write`
- 정규식(앵커 없는 JavaScript 정규식): `^Notebook`, `mcp__memory__.*`
- 전부: `"*"` 또는 생략

도구가 아닌 이벤트에서는 매처가 그 이벤트 고유의 값을 거릅니다. 예를 들어 `SessionStart` 는 `startup`, `resume`, `clear`, `compact`, `fork` 를 받아요. "새로 시작할 때만" 과 "컴팩션 직후에만" 을 구분해 걸 수 있다는 뜻입니다.

### 종료 코드 — exit 2 가 차단이다

훅에서 반드시 외워야 할 건 이것 하나입니다.

| 종료 코드 | 의미 |
|---|---|
| `0` | 성공. stdout 이 유효한 JSON 이면 JSON 으로, 아니면 평문으로 해석됩니다. `UserPromptSubmit` 과 `SessionStart` 에서는 Claude 에게 보이고, 그 밖에는 디버그 로그로만 남습니다 |
| **`2`** | **차단 오류.** 차단을 지원하는 이벤트(`PreToolUse`, `UserPromptSubmit`, `Stop`, `PostToolBatch` 등)에서 해당 동작이 막힙니다. JSON 으로 이 결정을 뒤집을 수 없습니다. 이유는 stderr 또는 JSON 의 결정 사유에서 옵니다 |
| 그 외 | 차단하지 않는 오류. 동작은 그대로 진행되며, 유효한 JSON 결정 필드는 존중됩니다 |

**차단하려면 stderr 에 이유를 쓰고 `exit 2`.** 이 한 줄이 "부탁"과 "강제"를 가르는 지점이에요. 3장에서 본 `CLAUDE.md` 의 문장은 아무리 굵게 써도 무시될 수 있지만, `exit 2` 는 무시할 수 없습니다.

이유를 stderr 에 쓰는 게 왜 중요한지도 짚고 갈까요? 차단만 하고 이유를 안 주면 에이전트는 같은 시도를 반복합니다. 4.3 절의 원칙이 여기서도 그대로 적용돼요 — **짧고, 무엇을 고칠지가 들어 있어야 합니다.**

더 세밀한 제어가 필요하면 stdout 으로 JSON 을 냅니다. `hookSpecificOutput` 아래에 `hookEventName`, `permissionDecision`(`allow` / `deny` / `escalate`), `permissionDecisionReason`, `additionalContext`, `updatedInput`, `systemMessage` 같은 필드를 담으시면 됩니다.

훅으로 들어오는 입력은 stdin 에 JSON 으로 옵니다. `session_id`, `transcript_path`, `cwd`, `permission_mode`, `hook_event_name` 이 공통이고, 도구 이벤트에서는 `tool_name`, `tool_input`, `tool_use_id` 가 추가돼요. 편집된 파일 경로가 필요하면 `tool_input` 에서 꺼내 씁니다.

### 훅으로 센서 출력을 다듬기

훅의 쓸모는 차단만이 아닙니다. **Claude 가 데이터를 보기 전에 전처리**할 수 있거든요. 4.3 절의 원칙을 실행에 옮기는 가장 직접적인 수단이 이것입니다.

예를 들어 1만 줄짜리 로그를 통째로 읽히는 대신, 훅이 `ERROR` 줄만 걸러서 넘긴다고 해봅시다. **수만 토큰이 수백 토큰이 됩니다.** 신호는 그대로 남고 잡음만 사라지죠. 센서의 판정력은 유지한 채 비용만 줄이는, 드문 종류의 개선입니다.

방법은 두 가지예요. `PostToolUse` 로 결과를 요약해 덧붙이거나, `PreToolUse` 로 **명령 자체를 바꿔치기**하는 것입니다. 뒤엣것이 더 깔끔해요. 애초에 장황한 출력이 생기지 않으니까요.

`PreToolUse` 훅은 stdin 으로 받은 JSON 을 보고, stdout 에 `hookSpecificOutput.updatedInput` 을 담아 **수정된 도구 입력**을 돌려줍니다. 이때 `permissionDecision: "allow"` 를 함께 내고요. 등록은 이렇게 합니다.

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "~/.claude/hooks/filter-test-output.sh"
          }
        ]
      }
    ]
  }
}
```

훅이 낼 stdout 의 모양은 이렇습니다. `command` 필드를 실패 줄만 남기는 형태로 바꿔서 돌려주는 거예요.

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "allow",
    "updatedInput": {
      "command": "python -m pytest -q 2>&1 | grep -E '^(FAILED|ERROR)' | head -20"
    }
  }
}
```

### 훅이 조용히 실패하는 것을 잡는 법

훅에는 고약한 성질이 하나 있습니다. **안 걸려도 티가 안 나요.** 경로 오타, 실행 권한 누락, 매처 불일치 — 어느 쪽이든 훅은 그냥 아무 일도 안 하고, 화면상으로는 평소와 똑같습니다. 그래서 "붙였다"고 믿은 채 몇 시간을 보내기 쉬워요.

확인은 두 단계로 합니다.

1. **`/hooks`** 를 실행해서 `PreToolUse` 아래에 내 훅이 실제로 나타나는지 봅니다. 여기 없으면 설정 파일이 안 읽힌 거예요.
2. **`claude --debug`** 로 실행합니다. 훅이 명령을 바꿨다면 디버그 로그에 `modified tool input keys: [command]` 가 찍힙니다. 이 줄이 없으면 훅이 실행되지 않았거나 출력이 유효한 JSON 이 아닌 겁니다.

신입 때 특히 몸에 붙여 두면 좋은 습관입니다. **훅을 붙였으면 붙었는지 확인하세요.** 확인하지 않은 훅은 없는 훅과 같고, 더 나쁘게는 있다고 착각하는 훅이니까요. 이 얘기는 4.9 절에서 더 밀고 나가겠습니다.

## 4.6 세 가지 규제 차원

무엇을 규제할 것인가로 하네스를 나누면 세 층이 나옵니다. Böckeler 의 분류이고, 뒤로 갈수록 **도구가 미성숙하다**는 점이 핵심이에요.

```mermaid
flowchart TB
    M["① 유지보수성 (Maintainability)<br/>구조 · 중복 · 복잡도 · 커버리지 · 스타일"]
    A["② 아키텍처 적합성 (Architecture Fitness)<br/>성능 · 관측 가능성 · 보안 · 모듈 경계"]
    B["③ 동작 (Behaviour)<br/>요청한 것을 실제로 하는가"]
    M -->|"도구 성숙도 ↓<br/>사람의 개입 필요 ↑"| A
    A -->|"도구 성숙도 ↓<br/>사람의 개입 필요 ↑"| B
```

**① 유지보수성 하네스.** 가장 성숙한 층입니다. 기존 정적 분석 도구가 거의 그대로 넘어와요. 결정적으로는 복잡도·중복 게이트와 커버리지 하한선, 추론적으로는 의미적으로 중복된 헬퍼나 증상만 덮은 임시방편을 잡아내는 리뷰 에이전트가 여기 옵니다. 그래서 **시작하기 가장 싼 지점**이에요. 한계는 분명합니다 — 어떤 도구도 "엉뚱한 걸 만들었다"는 잡지 못합니다.

**② 아키텍처 적합성 하네스.** 성능·관측 가능성·보안·모듈성 같은 횡단 품질을 **적합성 함수(fitness function)** 로 표현합니다. "아직 아키텍처적으로 괜찮은가"를 실행 가능한 정의로 바꾸는 거예요. 예를 들어 결제 엔드포인트의 p95 지연이 200ms 를 넘으면 실패하는 부하 테스트(센서)에, 성능 예산을 적어 둔 스킬(가이드)을 짝지어 줍니다. 에이전트가 빠른 속도로 코드를 바꿀 때 이런 품질은 **조용히** 무너지거든요. 신호로 만들어 두지 않으면 알 수가 없습니다.

**③ 동작 하네스.** Böckeler 가 가장 약하다고 말하는 층입니다. 지금 할 수 있는 건 사람이 쓴 기능 명세(피드포워드)에, AI 가 생성한 테스트와 커버리지 수치(피드백)를 붙이는 정도예요. 문제는 그 테스트를 **같은 부류의 모델이 썼다**는 점입니다. 검사 대상과 검사 도구가 같은 편향을 공유하는 거죠. 그래서 사람의 확인이 아직 빠질 수 없습니다.

③에서 그나마 쓸 만한 방법이 승인된 픽스처(approved fixtures) 방식이에요. 사람이 기대 출력을 한 번 승인해 두면, 이후 에이전트는 자기 실행 결과를 그 기준과 비교합니다. 사람이 쓴 계약 테스트나 BDD 시나리오를 코딩 **전에** 확보해 두는 것도 같은 발상이고요.

## 4.7 keep quality left — 검사를 어디에 둘 것인가

같은 검사라도 **언제 돌리느냐**가 효과를 가릅니다. 원칙은 "감당할 수 있는 가장 이른 단계에 둔다"예요.

사람에게 이 원칙은 "결함은 일찍 찾을수록 싸다"는 뜻이었습니다. 에이전트에게는 이유가 하나 더 붙어요. **이른 신호는 관련 맥락이 아직 컨텍스트 안에 있을 때 도착합니다.** 그래서 에이전트가 스스로 고칠 수 있고요. 30분 뒤 CI 에서 온 신호는 이미 컨텍스트에서 밀려난 코드에 대한 것입니다.

| 단계 | 두는 검사 | 성격 |
|---|---|---|
| 편집 직후 / 커밋 전 | 포매터, 린터, 변경 파일 단위 테스트, 가벼운 리뷰 에이전트 | 빠르고 쌉니다 |
| CI | 전체 테스트, 뮤테이션 테스트, 본격 아키텍처 리뷰 에이전트 | 느리고 비쌉니다 |
| 지속 | 데드 코드·의존성 드리프트 스캔, SLO 알림, 운영 응답 품질 샘플링 | 시간 축으로 감시 |

Claude Code 안에서 "커밋 전"은 `PostToolUse` 훅이나 `Stop` 훅으로 구현합니다. CI 는 이 저장소의 GitHub Actions 워크플로가 그 자리고요. 다음 절에서 실물을 같이 보시죠.

## 4.8 이 저장소를 읽어 보자

이 저장소의 센서는 두 개입니다. `scripts/check-docs.sh`(결정적)와 `.github/workflows/verify.yml`(둘을 배치하는 파이프라인)이에요. 각 검사가 어떤 종류의 센서인지 같이 분류해 봅시다.

### `scripts/check-docs.sh`

스크립트 맨 위 주석이 설계 의도를 밝혀 둡니다 — 사람이 아니라 CI 와 에이전트가 읽는 것을 전제로, 짧고 기계가 읽기 좋은 출력을 낸다고요. 4.3 절의 원칙을 그대로 구현한 것입니다. 출력은 `FAIL <무엇이 잘못됐는지>` 한 줄 형식이고, 마지막에 `VERDICT: PASS` 또는 `VERDICT: FAIL` 을 찍습니다. 종료 코드도 함께 주고요.

| 검사 | 무엇을 보나 | 분류 |
|---|---|---|
| 1. 챕터 필수 섹션 | 각 챕터에 4개 섹션과 검증일 메타가 있는가 | 결정적 · 유지보수성 |
| 2. 금지된 외부 이미지 | `docs/` 에 외부 URL 이미지 참조가 있는가 | 결정적 · **저작권 안전** |
| 3. 이전된 문서 URL | 구 `docs.claude.com` 경로를 쓰고 있는가 | 결정적 · 유지보수성 |
| 4. 코드 블록 짝 맞춤 | 백틱 펜스가 짝수 개인가 | 결정적 · 유지보수성 |
| 5. 시드 코드 테스트 | pytest 가 설치돼 있는가 + 실습용 결함이 **아직 살아 있는가** | 결정적 · 동작 |
| 6. 라이선스 고지 | `LICENSE`, `LICENSE-docs`, `SOURCES.md` 가 있는가 | 결정적 · 저작권 안전 |

5번이 재미있습니다. 보통 테스트는 통과해야 성공인데, 여기서는 **통과하면 실패**로 판정하거든요. `seed/todo-cli` 의 결함은 실습 재료니까요. 누군가(사람이든 에이전트든) 친절하게 고쳐 버리면 교보재가 사라집니다. 센서는 "테스트가 초록불인가"가 아니라 **"우리가 지키려는 성질이 유지되는가"** 를 재는 겁니다. 이 검사에는 사연이 좀 있어요. 4.9 절에서 이어가겠습니다.

4번도 눈여겨볼 만합니다. 백틱 개수를 세는 세 줄짜리 검사인데, 이게 없으면 문서 렌더링이 통째로 깨져요. **가장 값싼 결정적 센서가 가장 자주 값을 합니다.**

### 인용 안전성 검사는 왜 FAIL 조건인가

이 저장소에서 인용 안전성은 다른 검사와 지위가 다릅니다. `SOURCES.md` 의 집필 원칙은 원문과 **연속 15단어 이상 일치**하는 문장을 별도 항목으로 검사하고, **하나라도 걸리면 전체 검증 실패**로 처리한다고 못박아 뒀어요. `.claude/agents/verifier.md` 도 이 항목을 `LEGAL-RISK` 로 보고하며 "하나라도 있으면 전체 FAIL" 이라고 선언합니다.

왜 다를까요? 대부분의 결함은 **정도의 문제**입니다. 섹션이 하나 빠지면 문서가 조금 나쁘고, 고치면 원상복구되죠. 저작권 침해는 다릅니다. 게시되는 순간 되돌릴 수 없는 종류의 손해가 발생하고, 정도가 아니라 **성립하느냐 아니냐**의 문제니까요.

이런 성격의 검사를 경고로 두면 반드시 무시됩니다. 경고 목록이 길어지면 사람은 스크롤해서 넘기거든요. 그래서 되돌릴 수 없는 손해를 다루는 검사는 **경고가 아니라 게이트**여야 합니다.

동시에 이 검사는 **결정적 센서와 추론적 센서를 겹쳐 쓴 예**이기도 해요. `check-docs.sh` 2번(외부 이미지 차단)은 결정적으로 명백한 위반을 막습니다. 하지만 "번역투가 심해 원문 번역으로 의심되는 문단"은 정규식으로 잡을 수 없죠. 그건 verifier 에이전트가 의미를 읽고 판정합니다.

그리고 하나 더 — **집필한 주체가 검증하지 않습니다.** writer 에이전트에게 웹 도구가 없는 것(3장)이 원문 복제를 구조적으로 막는 가이드였다면, 별도의 verifier 에이전트는 그 결과를 검사하는 센서예요. 같은 규칙을 앞뒤로 두 번 거는 셈입니다.

### `.github/workflows/verify.yml`

워크플로 주석 자체가 이 파일을 센서의 실물 예제라고 밝혀 둡니다. 두 잡으로 나뉘어요.

**`structure` 잡**은 `check-docs.sh` 를 돌리고, 이어서 `.claude/settings.json` 을 포함한 저장소의 모든 JSON 을 실제로 파싱합니다. 설정 파일이 문법적으로 유효한지를 사람이 아니라 파서가 판정하는 거죠. 실패하면 빌드가 깨집니다 — **게이트**예요.

**`links` 잡**은 문서의 모든 URL 에 요청을 보내 죽은 링크를 셉니다. 여기에는 `continue-on-error: true` 가 붙어 있어요. 외부 사이트가 잠깐 죽었다고 우리 빌드를 깨뜨리지는 않겠다는 뜻입니다. 실패해도 빌드는 통과합니다 — **관측**이에요.

이 대비가 센서 설계의 실전 감각을 보여 줍니다. **우리가 통제할 수 있는 것은 게이트로, 통제할 수 없는 것은 관측으로 둡니다.** 통제할 수 없는 것을 게이트로 걸면 팀은 곧 그 검사를 꺼 버려요.

트리거 설정도 4.7 절의 "지속" 단계에 해당합니다. `push`, `pull_request` 외에 매주 월요일 `schedule` 이 걸려 있거든요. 아무도 커밋하지 않아도 문서는 낡습니다. 링크는 죽고 문서는 이전되고요. **시간 축으로 감시하는 센서**가 따로 필요한 이유입니다.

> 💭 **필자 견해**
>
> 검사를 처음 붙일 때는 전부 게이트로 걸고 싶어집니다. 하지만 게이트 하나가 오탐을 몇 번 내면 팀은 그 검사를 끄거나 우회해요. **꺼진 게이트는 관측보다 못합니다.** 새 검사는 관측으로 시작해서 오탐이 없다는 게 확인되면 게이트로 승격시키는 편이 오래 갑니다.

## 4.9 가장 위험한 센서는 고장 난 센서다

이 절의 사례는 지어낸 게 아닙니다. **이 자료를 만드는 도중에 이 저장소에서 실제로 일어난 일**이에요.

`check-docs.sh` 의 5번 검사는 원래 이렇게 생겼었습니다.

```bash
if python3 -m pytest seed/todo-cli/tests -q >/dev/null 2>&1; then
  err "테스트가 전부 통과함. 실습용 결함이 사라졌다"
else
  note "OK  시드 테스트가 예상대로 실패한다"
fi
```

읽어 보면 멀쩡해 보이죠. 실제로 이 센서는 `VERDICT: PASS` 를 냈습니다. 그런데 말이죠. 그 환경에는 **pytest 가 아예 설치되어 있지 않았습니다.**

무슨 일이 벌어진 건지 따라가 봅시다. `python3 -m pytest` 는 모듈이 없으니까 0 이 아닌 코드로 죽습니다. `if` 문은 그걸 "명령이 실패했다"로 읽고 `else` 로 갑니다. 그리고 `else` 는 "테스트가 예상대로 실패했다"고 안심시켜 주고요. **아무것도 검사하지 않으면서 통과 신호를 보내고 있었던 겁니다.**

### "실행 실패"와 "검사 실패"는 다르다

근본 원인은 종료 코드를 **뭉뚱그린** 데 있습니다. 0 이 아닌 코드는 여러 뜻을 담고 있거든요. 테스트가 실패했을 수도 있고, 도구가 없을 수도 있고, 테스트 수집 단계에서 에러가 났을 수도 있습니다. 이걸 하나로 묶어 버리면 센서는 거짓 안심을 줍니다.

다행히 pytest 는 종료 코드를 구분해서 줍니다. 그래서 고친 버전은 코드를 케이스로 나눴어요.

```bash
if ! python3 -m pytest --version >/dev/null 2>&1; then
  err "pytest 가 설치되어 있지 않아 시드 테스트를 검사할 수 없다 (pip install pytest)"
else
  python3 -m pytest seed/todo-cli/tests -q >/dev/null 2>&1
  case "$?" in
    0) err "seed/todo-cli: 테스트가 전부 통과함. 실습용 결함이 사라졌다" ;;
    1) note "OK  시드 테스트가 예상대로 실패한다" ;;
    *) err "seed/todo-cli: pytest 가 비정상 종료했다 (수집 오류 등). 종료 코드 $?" ;;
  esac
fi
```

세 가지가 달라졌습니다. 첫째, **도구가 있는지를 먼저 확인**합니다. 둘째, 종료 코드 0(전부 통과)과 1(테스트 실패)과 그 밖(비정상 종료)을 나눠서 읽습니다. 셋째, 판단할 수 없는 상황을 `note` 가 아니라 `err` 로 보고합니다.

### 센서는 자기가 살아 있음을 먼저 증명해야 한다

여기서 일반 원칙이 하나 나옵니다. **도구 존재 확인은 검사의 일부입니다.** 센서가 "대상이 건강한가"를 재기 전에, 자기 자신이 실제로 재고 있는지를 먼저 증명해야 해요. 그리고 확인할 수 없는 상태는 통과가 아니라 실패로 보고해야 하고요.

이건 CI 만의 문제가 아닙니다. 4.5 절에서 본 훅의 조용한 실패도 같은 종류예요. 경로 오타 하나로 훅이 안 걸려도 화면은 평소와 똑같죠. 그래서 `/hooks` 로 등록을 확인하고 `claude --debug` 로 실제 동작을 확인하라고 말씀드린 겁니다.

### 없는 센서보다 고장 난 센서가 위험하다

이 사건의 교훈은 여기 있습니다. 센서가 아예 **없으면** 사람이 직접 봅니다. 불편하지만 안전해요. 센서가 **고장 나 있으면** 사람이 안 봅니다. 초록불이 떠 있으니까요.

즉 고장 난 센서는 검사를 못 할 뿐 아니라, **사람의 주의까지 걷어갑니다.** 순수하게 마이너스예요.

### 그래서 센서를 테스트하라

확인법은 단순합니다. **일부러 통과 조건을 깨뜨려 보고, 센서가 실제로 FAIL 을 내는지 봅니다.** 통과하는 것만 보고 센서를 믿으시면 안 돼요. 실패해야 할 때 실패하는지를 봐야 합니다.

새 검사를 붙일 때 이 한 단계를 습관으로 만들어 두면, 이 절의 사고는 거의 전부 예방됩니다. 실습 C 에서 직접 해 볼 거예요.

이 문제는 6장의 자율 루프로 가면 훨씬 심각해집니다. 루프는 센서의 판정을 **종료 조건**으로 쓰니까요. 게이트가 이런 식으로 고장 나 있으면, 에이전트는 아무 검증 없이 코드를 무한히 갈아엎으면서 매 회차 "통과했습니다"를 보고하게 됩니다.

> 💭 **필자 견해**
>
> 이 버그가 제 눈에 띈 건 실습 환경을 새로 만들다가 `pip install pytest` 를 빼먹었기 때문입니다. 순전히 우연이에요. 그게 무섭습니다. **고장 난 센서는 스스로 신고하지 않거든요.** 그래서 저는 이제 검사를 새로 쓸 때마다 짝이 되는 "일부러 깨뜨리기" 절차를 주석으로 같이 적어 둡니다.

## 직접 해보기

### 실습 A. 실패하는 테스트를 센서로 삼기

`seed/todo-cli` 의 테스트는 지금 실패합니다. 이걸 첫 센서로 써 봅시다.

**1단계. 신호를 먼저 눈으로 봅니다.**

```bash
python -m pytest seed/todo-cli/tests -q
```

어떤 테스트가 왜 실패하는지 출력을 읽어 보세요. 4.3 절 기준으로 이 출력이 좋은 센서 출력인지 판단해 보시고요.

**2단계. 에이전트에게 지시합니다.**

여기서 프롬프트가 중요합니다. **테스트를 고치지 말고 통과시키라**고 명시하셔야 해요.

> `seed/todo-cli/tests` 의 테스트를 통과시켜라. 단 **테스트 파일은 절대 수정하지 않는다.** 테스트는 사양이다. 구현(`storage.py`)만 고친다. 끝나면 `python -m pytest seed/todo-cli/tests -q` 를 실행하고 그 출력을 그대로 보여 준다.

마지막 문장을 빼시면 안 됩니다. **증거를 요구하는 부분**이거든요.

**3단계. 무슨 일이 일어났는지 확인합니다.**

```bash
git diff --stat seed/todo-cli
```

`tests/` 아래 파일이 변경 목록에 있다면, 지시는 지켜지지 않은 겁니다. 이것이 3장의 결론 — **가이드는 부탁일 뿐**이라는 것 — 의 실물 증거예요. 그러면 강제 단계 사다리를 한 칸 올라갈 차례입니다.

### 실습 B. PostToolUse 훅으로 자동 검사 붙이기

편집이 일어날 때마다 테스트가 자동으로 돌게 만들어 봅시다.

**1단계.** 훅 스크립트를 `.claude/hooks/run-seed-tests.sh` 로 만듭니다.

```bash
#!/usr/bin/env bash
# 편집 직후 시드 테스트를 돌리고, 결과를 짧게 되돌려 준다.
cd "$CLAUDE_PROJECT_DIR" || exit 0
out=$(python3 -m pytest seed/todo-cli/tests -q 2>&1 | tail -5)
printf 'seed tests:\n%s\n' "$out"
exit 0
```

`tail -5` 가 핵심입니다. 전체 출력을 그대로 흘려보내면 컨텍스트만 먹거든요. 실행 권한 부여도 잊지 마세요.

```bash
chmod +x .claude/hooks/run-seed-tests.sh
```

**2단계.** `.claude/settings.json` 의 `hooks` 키에 등록합니다. 이 저장소의 기존 `permissions` 키 옆에 나란히 두시면 됩니다.

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/run-seed-tests.sh"
          }
        ]
      }
    ]
  }
}
```

**3단계.** 실습 A 의 2단계를 다시 시켜 봅니다. 이제 파일을 하나 고칠 때마다 테스트 결과가 따라붙어요. 에이전트가 자기 변경의 효과를 즉시 보게 되는 것 — 이게 루프가 닫힌 상태입니다.

**4단계 (심화). 차단하는 훅을 만듭니다.**

이번엔 테스트 파일 수정 자체를 막아 봅시다. `PreToolUse` 로 붙이고, 대상 경로가 `seed/todo-cli/tests` 를 포함하면 stderr 에 이유를 쓰고 `exit 2` 로 끝냅니다.

```bash
#!/usr/bin/env bash
# PreToolUse: 실습용 테스트 파일 수정을 차단한다.
payload=$(cat)
case "$payload" in
  *seed/todo-cli/tests*)
    echo "테스트 파일은 실습 과제의 사양이다. storage.py 를 고칠 것." >&2
    exit 2
    ;;
esac
exit 0
```

훅 입력은 stdin 에 JSON 으로 오니까 `cat` 으로 받습니다. 위 예제는 문자열 매칭으로 단순화한 것이고, 실제로는 `tool_input` 의 경로 필드를 파싱하는 편이 정확해요.

이제 실습 A 의 3단계를 다시 해 보세요. `git diff --stat` 에 `tests/` 가 나타나지 않습니다. **부탁이 강제가 된 순간**이에요.

**5단계 (필수). 훅이 진짜 걸렸는지 확인합니다.**

훅은 안 걸려도 티가 안 납니다. 그러니 붙였으면 확인하세요.

- `/hooks` 를 실행해 `PostToolUse` / `PreToolUse` 아래에 내 스크립트가 보이는지 봅니다.
- `claude --debug` 로 세션을 열어 실제 실행 로그를 봅니다. `PreToolUse` 훅이 명령을 바꿨다면 `modified tool input keys: [command]` 가 찍힙니다.

둘 다 안 보이면 붙지 않은 겁니다. 경로, 실행 권한(`chmod +x`), 매처 철자를 순서대로 의심해 보세요.

**6단계.** 실습이 끝나면 원상복구합니다. `git checkout -- seed/todo-cli` 로 시드 코드를 되돌리고 `./scripts/check-docs.sh` 를 돌려 `VERDICT: PASS` 를 확인하세요. 5번 검사가 실습용 결함이 제자리에 있는지 알려 줍니다.

### 실습 C. 센서를 일부러 깨뜨려 보기

4.9 절의 사고를 직접 재현하고 예방법을 몸에 익히는 실습입니다. **통과하는 것만 보고 센서를 믿지 않는 연습**이에요.

**1단계. 정상 상태를 확인합니다.**

```bash
./scripts/check-docs.sh; echo "exit=$?"
```

`VERDICT: PASS` 와 `exit=0` 이 나오는지 봅니다.

**2단계. 통과 조건을 일부러 깨뜨립니다.**

여러 검사 중 하나를 골라 위반을 만들어 보세요. 가장 안전한 건 4번(백틱 짝 맞춤)입니다. 아무 챕터 파일 끝에 백틱 세 개를 한 줄 추가하고, 다시 돌립니다.

```bash
./scripts/check-docs.sh; echo "exit=$?"
```

`FAIL ...` 한 줄과 `VERDICT: FAIL`, `exit=1` 이 나와야 합니다. **나오지 않는다면 그 검사는 고장 나 있는 거예요.** 추가한 줄은 바로 지우시고요.

**3단계. 5번 검사를 깨뜨려 봅니다.**

`seed/todo-cli/storage.py` 의 `add` 함수 기본 인자를 고쳐 테스트를 전부 통과시킨 뒤 스크립트를 돌립니다. 이번엔 **테스트가 통과했다는 이유로** `FAIL` 이 떠야 해요. 확인하셨으면 `git checkout -- seed/todo-cli` 로 되돌립니다.

**4단계. 도구를 없애 봅니다 (핵심).**

pytest 가 없는 환경을 흉내 내 봅시다. 가상환경을 새로 만들고, pytest 를 설치하지 않은 채 스크립트를 돌립니다.

```bash
python3 -m venv /tmp/no-pytest && /tmp/no-pytest/bin/python -m pytest --version; echo "exit=$?"
```

이 상태에서 5번 검사가 어떻게 판정해야 하는지, 스크립트를 읽고 확인해 보세요. 현재 버전은 `pytest 가 설치되어 있지 않아 시드 테스트를 검사할 수 없다` 로 **FAIL** 을 냅니다. 4.9 절의 옛 버전이었다면 조용히 통과했을 상황이죠.

**5단계. 내가 만든 훅에도 같은 걸 합니다.**

실습 B 의 차단 훅이 정말 차단하는지 확인해 보세요. 에이전트에게 일부러 테스트 파일을 고치라고 시켜 보고, 실제로 막히는지 봅니다. 막히지 않는다면 훅은 걸려 있지 않은 거예요.
