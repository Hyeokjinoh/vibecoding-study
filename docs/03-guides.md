# 3. Guides — 행동하기 전에 방향을 준다

> **검증일**: 2026-08-28 · **Claude Code**: v2.1.247

## 한 줄 요약

가이드(Guides)는 에이전트가 **행동하기 전에** 방향을 주는 통제다. Claude Code 에서는 `CLAUDE.md`, `.claude/rules/`, 스킬(Agent Skills) 세 가지 모양으로 구현되며, 셋 다 강제가 아니라 **부탁**이라는 한계를 함께 배워야 한다.

---

## 3.1 가이드란 무엇인가

앞 장에서 하네스(harness)를 두 방향으로 나눴다. 행동 **전**에 거는 통제와 행동 **후**에 되돌리는 통제다. 앞쪽이 가이드(Guides), 뒤쪽이 센서(Sensors)다. 이 구분은 Birgitta Böckeler 가 "Harness Engineering for Coding Agent Users"(martinfowler.com)에서 제시한 분류를 따른다.

가이드의 목적은 단순하다. **첫 시도가 맞을 확률을 올리는 것**이다. 에이전트가 우리 팀의 관례를 모른 채 코드를 쓰면, 매번 같은 실수를 하고 매번 사람이 같은 지적을 반복하게 된다. 그 지적을 한 번 문서로 굳혀 두면 그 실수는 애초에 발생하지 않는다.

센서만 있는 하네스를 상상해 보자. 에이전트가 틀린 코드를 쓰고, 테스트가 잡고, 다시 고친다. 결과는 맞지만 매 세션 같은 왕복을 반복한다. 반대로 가이드만 있으면 규칙이 지켜졌는지 아무도 확인하지 않는다. Böckeler 의 요지는 둘 다 필요하다는 것이다.

### 가이드와 센서 대비

| | **가이드 (Guides)** | **센서 (Sensors)** |
|---|---|---|
| 작동 시점 | 에이전트가 행동하기 **전** | 에이전트가 행동한 **후** |
| 제어 방식 | 피드포워드(feedforward) | 피드백(feedback) |
| 목적 | 첫 시도의 정확도를 올린다 | 틀린 결과를 발견해 되돌린다 |
| 비용 | 매 세션 컨텍스트를 차지한다 | 실행 시간·CI 시간을 차지한다 |
| 실패 모드 | 지켜졌는지 아무도 모른다 | 같은 실수를 매번 다시 잡는다 |
| 대표 예 | `CLAUDE.md`, 스킬, 타입 스텁 | 테스트, 린터, 리뷰 에이전트 |

### 2×2 격자

가이드/센서 축에, 검사가 결정적인지 의미적인지를 묻는 축을 하나 더 얹으면 격자가 된다. 결정적 통제(computational)는 CPU 가 실행하고 같은 입력에 항상 같은 판정을 낸다. 추론적 통제(inferential)는 모델의 판단에 기대므로 느리고 흔들리지만, 규칙으로 표현할 수 없는 것을 본다.

|  | **결정적 (Computational)** | **추론적 (Inferential)** |
|---|---|---|
| **가이드 (전)** | 언어 서버, 타입 스텁, 프로젝트의 일관된 디렉터리 구조 | `CLAUDE.md`, `.claude/rules/`, 스킬 |
| **센서 (후)** | 테스트, 린터, 타입 체커, `check-docs.sh` | 리뷰 서브에이전트, LLM 이 읽도록 쓴 린트 메시지 |

이 격자의 쓸모는 감사(audit)에 있다. 지금 우리 저장소의 통제를 네 칸에 배치해 보면, **비어 있는 칸이 곧 하네스의 구멍**이다. 이 장은 오른쪽 위 칸을 다루고, 다음 장이 아래 두 칸을 다룬다.

```mermaid
flowchart LR
    subgraph G["가이드 — 행동 전"]
        G1["결정적<br/>언어 서버 · 타입 · 구조"]
        G2["추론적<br/>CLAUDE.md · rules · 스킬"]
    end
    A(("코딩<br/>에이전트"))
    subgraph S["센서 — 행동 후"]
        S1["결정적<br/>테스트 · 린터 · 타입 체커"]
        S2["추론적<br/>리뷰 에이전트"]
    end
    G1 --> A
    G2 --> A
    A --> S1
    A --> S2
    S1 -- "짧은 실패 메시지" --> A
    S2 -- "리뷰 지적" --> A
```

## 3.2 CLAUDE.md — 매 세션 자동으로 실리는 문서

`CLAUDE.md` 는 대화가 시작될 때 자동으로 컨텍스트에 실리는 프로젝트 문서다. 코드만 봐서는 알 수 없는 것 — 빌드 명령, 테스트 실행 방법, 팀의 관례, 환경의 함정 — 을 적는 자리다.

중요한 성질이 하나 있다. `CLAUDE.md` 는 시스템 프롬프트 뒤에 **사용자 메시지 형태로 전달**된다. 즉 강제되는 설정이 아니라 그냥 문맥이다. 반드시 지켜져야 하는 것이라면 문서가 아니라 훅(hook)으로 내려야 한다. 이 얘기는 4장에서 이어간다.

### 네 개의 스코프

파일은 네 층위로 나뉘고, **넓은 것부터 좁은 것 순서로** 로드된다. 뒤에 오는 내용일수록 모델에 더 가깝게 놓인다.

| 순서 | 스코프 | 위치 | 성격 |
|---|---|---|---|
| 1 | 관리형 정책 | 조직이 배포 (macOS `/Library/Application Support/ClaudeCode/CLAUDE.md`) | 제외할 수 없다 |
| 2 | 사용자 | `~/.claude/CLAUDE.md` | 내 모든 프로젝트에 적용 |
| 3 | 프로젝트 | `./CLAUDE.md` 또는 `./.claude/CLAUDE.md` | 커밋해서 팀이 공유 |
| 4 | 개인 로컬 | `./CLAUDE.local.md` | 나만. gitignore 대상 |

핵심은 **덮어쓰기가 아니라 이어붙임**이라는 점이다. 파일시스템 루트에서 현재 디렉터리까지의 모든 `CLAUDE.md` 와 `CLAUDE.local.md` 가 실행 시점에 전부 이어붙는다. 같은 디렉터리 안에서는 `CLAUDE.md` 다음에 `CLAUDE.local.md` 가 붙는다.

현재 디렉터리보다 **아래**에 있는 파일은 다르게 동작한다. 시작할 때 실리지 않고, Claude 가 그 디렉터리의 파일을 실제로 읽을 때 지연 로드된다. 모노레포에서 패키지별 규칙을 나눠 두면 필요한 것만 실린다는 뜻이다.

모노레포에서 위쪽 조상 디렉터리의 `CLAUDE.md` 가 방해가 된다면 `claudeMdExcludes` 설정에 글롭 목록을 주어 건너뛸 수 있다. 단 관리형 정책 파일은 제외 대상이 아니다.

```mermaid
flowchart TB
    P["관리형 정책<br/>조직 배포"] --> U["사용자<br/>~/.claude/CLAUDE.md"]
    U --> R["프로젝트 루트<br/>./CLAUDE.md"]
    R --> L["./CLAUDE.local.md"]
    L --> C["하위 디렉터리 CLAUDE.md<br/>(그 폴더를 읽을 때 지연 로드)"]
    C --> X["최종 컨텍스트<br/>= 전부 이어붙인 결과"]
```

### `@경로` import

`CLAUDE.md` 안에 `@docs/git-instructions.md` 처럼 쓰면 그 파일을 컨텍스트로 끌어온다. 상대 경로는 **가져오는 파일 기준**으로 풀린다. 가져온 파일이 또 다른 파일을 가져오는 재귀도 되고, 최대 **4홉**까지다.

한 가지 함정이 있다. import 는 컨텍스트를 **아끼지 못한다.** 가져온 파일도 결국 실행 시점에 전부 로드되기 때문이다. 파일을 쪼갠 만큼 컨텍스트가 줄어들 거라 기대하면 안 된다. 실제로 줄이려면 뒤에 나올 경로 스코프 규칙이나 스킬을 써야 한다.

백틱 안이나 코드 블록 안의 `@` 경로는 import 로 취급되지 않는다. 문서에서 경로를 예시로 보여 줄 때 유용한 성질이다. 그리고 프로젝트 파일의 import 가 작업 디렉터리 밖을 가리키면 최초 1회 승인 대화상자가 뜬다.

`AGENTS.md` 를 쓰는 팀이라면 알아 둘 것이 있다. Claude Code 가 읽는 파일 이름은 `CLAUDE.md` 다. `CLAUDE.md` 에서 `@AGENTS.md` 로 가져오거나 심볼릭 링크를 걸어 다리를 놓는다.

### `/init` 과 `/memory`

`/init` 은 코드베이스를 훑어 초안 `CLAUDE.md` 를 만들어 준다. 이미 파일이 있으면 덮어쓰지 않고 개선안을 제안한다. Cursor 의 `.cursor/rules/`·`.cursorrules` 와 Copilot 의 `.github/copilot-instructions.md` 도 함께 읽으므로, 다른 도구를 쓰던 저장소에서 이사 올 때 편하다.

`/memory` 는 사용자·프로젝트 스코프에 걸친 메모리 파일 목록을 보여 주고, 고른 파일을 편집기로 연다(없으면 만들어 준다). 이번 세션에 **실제로 무엇이 로드됐는지** 확인하려면 `/context` 를 쓴다. 규칙이 안 먹는 것 같을 때 첫 번째로 확인할 곳이다.

## 3.3 무엇을 넣고 무엇을 빼는가

여기가 이 장에서 가장 중요한 절이다. `CLAUDE.md` 를 늘리는 것은 공짜가 아니다. 이 파일의 비용은 **모든 대화에서** 지불된다. 그리고 컨텍스트가 길어질수록 모델의 정확도는 떨어진다. 어텐션이 토큰 수의 제곱에 비례해 분산되기 때문이다.

그래서 결과가 뒤집힌다. 규칙을 900줄 적어 두면 7번 규칙이 조용히 무시된다. 40줄로 줄이면 다시 지켜진다. **파일을 늘리는 행위가 규칙 준수율을 떨어뜨린다.** 문서를 많이 쓸수록 통제가 강해질 거라는 직관은 여기서 틀린다.

### 판단 기준

한 줄을 넣을지 말지는 이 질문으로 정한다.

> **이 줄을 지우면 에이전트가 실수를 하는가?**

답이 "아니오"면 뺀다. 이 기준을 통과하는 것은 대개 **매번 다시 설명하게 되는 것**들이다. 두 번 이상 같은 지적을 했다면 그건 문서에 들어갈 자격이 있다. 한 번도 지적한 적 없는 일반론은 자격이 없다.

| 넣는다 | 뺀다 |
|---|---|
| "전체 스위트 대신 단일 테스트를 우선 실행한다" | "깨끗한 코드를 작성하라" |
| "이 저장소는 pnpm 을 쓴다. npm 을 쓰면 lockfile 이 깨진다" | 파일별 역할 설명 (코드를 읽으면 안다) |
| "라이선스 문제로 X 라이브러리를 쓰지 않는다" | 언어 문법·표준 라이브러리 설명 |
| 로컬 환경의 함정, 재현 안 되는 셋업 절차 | 린터가 이미 잡는 스타일 규칙 |

오른쪽 마지막 항목을 눈여겨보자. 린터가 잡는 것을 문서에도 적으면 컨텍스트만 쓰고 얻는 게 없다. **결정적 센서가 이미 커버하는 것은 추론적 가이드에 중복해서 넣지 않는다.**

### 컨텍스트 예산 — 항상 로드 vs 필요할 때 로드

앞의 기준은 감각에 기대는 면이 있다. 다행히 더 기계적인 기준이 있다. **로드 시점**이다.

`CLAUDE.md` 는 **세션 시작 시** 컨텍스트에 실린다. 그래서 특정 워크플로에만 쓰이는 상세 지시를 여기 넣으면, 그 워크플로와 아무 상관 없는 작업을 할 때도 그 토큰을 **계속 지불한다.** 배포 절차 30줄을 `CLAUDE.md` 에 적어 두면, 오타 하나 고치는 세션에서도 그 30줄이 실린다.

스킬은 다르다. **호출될 때만** 로드된다. 그래서 전문적인 지시를 스킬로 옮기면 기본 컨텍스트가 그만큼 작아진다. 같은 내용이 같은 저장소에 있어도, 어디에 두느냐에 따라 상시 비용이냐 조건부 비용이냐가 갈린다.

공식 권장치도 명확하다. **`CLAUDE.md` 는 200줄 이하로 유지하고, 필수적인 것만 넣는다.** (4 MiB 를 넘는 파일은 아예 건너뛴다.) 이 숫자를 예산 상한으로 놓고 아래 규칙을 적용하면 판단이 기계적으로 정리된다.

| 이 규칙은… | 어디에 두나 | 지불 시점 |
|---|---|---|
| 어떤 작업을 하든 필요하다 | `CLAUDE.md` | 매 세션 (상시) |
| 특정 경로를 건드릴 때만 필요하다 | `.claude/rules/` + `paths:` | 그 파일을 만질 때 |
| 특정 작업을 할 때만 필요하다 | 스킬 (`SKILL.md`) | 호출될 때 |
| 매번 반드시 일어나야 한다 | 훅 | 실행되지만 컨텍스트를 안 먹는다 |

마지막 줄이 흥미롭다. 훅은 강제력이 셀 뿐 아니라 **컨텍스트 예산 면에서도 유리하다.** 규칙을 문장으로 설명해서 모델에게 매번 읽히는 대신, 스크립트가 조용히 처리한다. 그래서 에이전트가 자꾸 어기는 규칙은 훅으로 올리는 것이 두 배로 남는 거래다.

예산이 어디에 쓰이는지는 추측하지 말고 재라. `/context` 는 지금 무엇이 컨텍스트를 차지하고 있는지 보여 준다. `/usage` 는 세션의 토큰 사용량 통계를 보여 주고, 플랜에 따라 스킬·서브에이전트·플러그인·MCP 서버별 귀속(attribution) 내역까지 보여 준다. 상태 표시줄에 컨텍스트 사용량을 상시 띄워 두는 설정도 있다.

> 💭 **필자 견해**
>
> "짧게 쓰라"는 조언은 지키기 어렵다. 기준이 취향처럼 들리기 때문이다. **로드 시점**으로 바꿔 물으면 다툼이 사라진다. "이건 매 세션 실려야 하는가?"에 아니라고 답하는 순간 옮길 곳이 정해진다.

> 💭 **필자 견해**
>
> `CLAUDE.md` 는 위키가 아니라 **체크리스트**로 취급하는 편이 낫다. 새 규칙을 넣을 때마다 오래된 줄 하나를 지울 후보로 검토하면 파일이 저절로 관리된다. 실제로 나는 챕터 하나를 쓸 때마다 이 저장소의 `CLAUDE.md` 를 다시 읽고, "이건 이제 훅으로 내려도 되겠다" 싶은 줄을 찾는다.

## 3.4 `.claude/rules/` 와 경로 스코프

`CLAUDE.md` 하나에 모든 규칙을 담으면 앞 절의 비대화 문제를 피할 수 없다. `.claude/rules/*.md` 는 규칙을 주제별 파일로 쪼개는 장치다. 하위 디렉터리까지 재귀적으로 탐색된다. `~/.claude/rules/` 는 사용자 스코프로 동작하며, 사용자 규칙이 프로젝트 규칙보다 먼저 로드된다.

진짜 이득은 `paths:` frontmatter 에 있다. 글롭 목록을 적어 두면 그 패턴에 맞는 파일을 Claude 가 건드릴 때만 규칙이 로드된다. import 와 달리 **이건 실제로 컨텍스트를 아낀다.**

`.claude/rules/api.md` 를 이렇게 쓴다.

```markdown
---
paths:
  - "src/api/**/*.ts"
---
모든 API 엔드포인트는 입력을 검증한다.
```

`paths` 가 없는 규칙 파일은 시작할 때 로드되며, 우선순위는 `.claude/CLAUDE.md` 와 같다.

즉 규칙은 세 등급으로 나뉜다. **항상 필요한 것**은 `CLAUDE.md`, **특정 경로에서만 필요한 것**은 `paths:` 규칙, **특정 작업에서만 필요한 것**은 스킬이다. 이 세 등급을 구분해 쓰는 것이 컨텍스트 예산 관리의 실무다.

## 3.5 Agent Skills — 필요할 때 불러오는 가이드

스킬은 `SKILL.md` 파일 하나에 담긴 지시 묶음이다. 놓는 자리는 이렇다.

- 프로젝트: `.claude/skills/<skill-name>/SKILL.md`
- 개인: `~/.claude/skills/<skill-name>/SKILL.md`
- 플러그인: `<plugin>/skills/<skill-name>/SKILL.md`

이름이 겹치면 엔터프라이즈 > 개인 > 프로젝트 순으로 이긴다. 그리고 이 셋 중 무엇이든 같은 이름의 번들 스킬을 덮어쓴다.

frontmatter 필드는 전부 선택이지만 `description` 은 사실상 필수다. `name` 은 표시 이름이고, 생략하면 디렉터리 이름이 쓰인다. 그 밖에 `when_to_use`, `argument-hint`, `allowed-tools`, `disallowed-tools`, `model`, `disable-model-invocation`, `user-invocable`, `paths` 같은 필드를 쓸 수 있다.

### 점진적 공개 (progressive disclosure)

스킬의 핵심 설계는 이것이다. 컨텍스트에 상주하는 것은 스킬의 **설명뿐**이다. 본문은 실제로 호출될 때만 로드된다. 그래서 긴 참고 자료를 스킬로 만들어도 쓰이기 전까지는 컨텍스트를 거의 쓰지 않는다.

왜 전부 다 먹이지 않는가? 3.3 절의 이유와 같다. 컨텍스트는 유한한 예산이고, 지금 안 쓰는 문서가 지금 쓰는 규칙의 준수율을 갉아먹기 때문이다. 스킬은 "목차만 들고 있다가 필요할 때 펼친다"는 전략의 구현이다.

여기서 실무적으로 중요한 제약이 나온다. 목록에 실리는 `description` + `when_to_use` 합계는 **1,536자에서 잘린다.** 잘리면 Claude 가 그 스킬을 언제 써야 하는지 모르게 된다. 그러니 **핵심 사용 사례를 맨 앞에 쓴다.**

호출 주체도 고를 수 있다. 기본은 사람과 모델 둘 다다. `disable-model-invocation: true` 면 사람만 부를 수 있고, 이 경우 설명조차 컨텍스트에 남지 않는다. `user-invocable: false` 면 모델만 쓰고 `/` 메뉴에서는 숨는다.

한 가지 수명 특성을 기억하자. 한 번 호출된 `SKILL.md` 는 그 세션 내내 대화에 남고, 이후 턴에서 파일을 다시 읽지 않는다. 스킬 파일을 고쳤다면 세션을 새로 시작해야 반영된다.

본문에 백틱 느낌표 형식으로 셸 명령을 적어 두면 Claude 가 보기 전에 실행되고 그 출력으로 치환된다. `git diff HEAD` 같은 것을 넣어 두면 스킬이 항상 현재 상태를 들고 시작한다.

### 슬래시 커맨드는 스킬로 통합됐다

예전에 따로 있던 커스텀 슬래시 커맨드는 스킬로 흡수됐다. `.claude/commands/deploy.md` 와 `.claude/skills/deploy/SKILL.md` 는 **둘 다 `/deploy` 를 만들고 동작도 같다.** 기존 `.claude/commands/` 파일은 계속 동작하므로 급히 옮길 필요는 없다.

스킬 쪽 형식이 나은 점은 두 가지다. 보조 파일을 둘 디렉터리가 생기고, frontmatter 가 더 풍부하다. 인자는 `$ARGUMENTS` 로 전부 받거나 `$0`, `$1` 처럼 위치로 받는다. 한 메시지 앞머리에 커맨드를 여러 개 쌓아 부를 수도 있다(첫 스킬 + 최대 5개).

배포처럼 위험한 커맨드에는 `disable-model-invocation: true` 를 붙이는 것이 안전하다. 모델이 알아서 `/deploy` 를 쏘는 일을 구조적으로 막는다.

## 3.6 이 저장소를 읽어 보자

이 저장소의 루트 `CLAUDE.md` 자체가 교보재다. 실제로 무엇이 들어 있고 왜 들어 있는지 뜯어보자.

첫 문단은 이 저장소가 학습 자료인 **동시에** 자료가 가르치는 하네스의 실물 예제라고 선언하고, `.claude/` 아래 설정을 지우거나 단순화하지 말라고 못박는다. 이건 코드를 읽어서는 절대 알 수 없는 정보다. 정리 좋아하는 에이전트가 "중복 설정을 정리했습니다"라며 교보재를 지우는 사고를 막는다.

그다음 저장소 구조 표에서 `docs/_facts/` 를 "집필의 유일한 근거"로, `seed/todo-cli/` 를 "의도적으로 결함이 있다"로 표시한다. 특히 뒤엣것이 결정적이다. 실습용 버그를 만난 에이전트의 기본 반응은 고치는 것이므로, **고치지 말라**는 지시가 명시적으로 필요하다. 규칙 4번이 "시키지 않으면 고치지 않는다"로 한 번 더 강조한다.

"절대 규칙" 1번은 저작권 안전이다. 문장을 옮기지 말고, 인용은 15단어 미만 정의구에 한하며, 외부 이미지 대신 Mermaid 로 그리라고 한다. 2번은 근거 없는 서술 금지와 `<!-- NEED-FACT: 질문 -->` 표기법이다. 둘 다 "매번 다시 설명하게 되는 것"의 전형이라 문서에 들어갈 자격이 있다.

문체 절도 마찬가지다. 독자 정의, 용어 병기 규칙, 한 문단 4줄 제한, 견해 블록 분리. 이걸 안 적으면 매 챕터마다 같은 지적을 하게 된다. 반대로 이 파일에 없는 것도 보자. 문법 설명도, 파일별 역할 나열도, "좋은 글을 써라" 같은 문장도 없다.

### "writer 에게 웹 도구를 주지 않는다"는 왜 가이드가 아닌가

규칙 3번에 이런 줄이 있다.

> 집필은 `writer` 에이전트가 한다. **writer 에게는 웹 도구를 주지 않는다.**

문장만 보면 가이드처럼 보인다. 하지만 실제 강제력은 이 문장에 없다. `.claude/agents/writer.md` 의 frontmatter 에 있다.

```yaml
tools: Read, Write, Edit, Grep, Glob
```

서브에이전트의 `tools` 필드는 허용 도구 목록이고, 생략하면 전부 상속한다. 여기서는 명시했으므로 writer 에게 웹 도구는 **존재하지 않는다.** 지켜 달라는 부탁이 아니라, 어길 수 있는 경로 자체가 없는 상태다.

이 차이가 이 장 전체의 결론이다. `CLAUDE.md` 의 문장은 모델이 읽고 따를 수도 있고 긴 세션 끝에 잊을 수도 있다. `tools` 목록은 모델의 협조와 무관하게 도구 목록을 결정한다. 앞엣것이 추론적 통제, 뒤엣것이 결정적 통제다.

그러면 `CLAUDE.md` 의 그 문장은 왜 남겨 뒀을까. 대상이 다르기 때문이다. `tools` 필드는 writer 를 구속하지만, `CLAUDE.md` 의 문장은 **이 저장소를 손대는 다음 사람과 다음 에이전트**에게 그 구속을 지우지 말라고 알린다. 강제 장치의 존재 이유를 적어 두는 것도 가이드의 일이다.

> 💭 **필자 견해**
>
> 하네스를 설계할 때 나는 이 순서로 자문한다. **"이걸 못 하게 만들 수 있나?"** → 안 되면 **"이걸 자동으로 잡을 수 있나?"** → 그것도 안 되면 그제야 문서에 적는다. 문서부터 쓰기 시작하면 문서만 길어지고 아무것도 강제되지 않는다.

## 3.7 가이드는 부탁이지 강제가 아니다

정리하자. 이 장에서 다룬 세 장치는 전부 **추론적 통제**다. 모델이 텍스트를 읽고 따라 줄 때만 작동한다.

| 장치 | 로드 시점 | 성격 | 강제력 |
|---|---|---|---|
| `CLAUDE.md` | 세션 시작 시 항상 | 추론적 | 없음 (권고) |
| `.claude/rules/` + `paths:` | 해당 경로를 건드릴 때 | 추론적 | 없음 (권고) |
| 스킬 | 호출될 때 | 추론적 | 없음 (권고) |
| 서브에이전트 `tools` | 에이전트 실행 시 | 결정적 | 있음 (구조적) |
| 훅 | 정해진 생애주기 시점 | 결정적 | 있음 (차단 가능) |

위 세 줄과 아래 두 줄 사이에 선이 그어져 있다. 위쪽은 아무리 굵은 글씨로 써도 무시될 수 있다. **반드시 매번 일어나야 하는 일이라면 가이드가 아니라 훅으로 내려야 한다.**

그래서 다음 장의 주제는 자연스럽게 정해진다. 행동한 뒤에 되돌리는 통제 — 센서와 훅이다.

## 직접 해보기

`seed/todo-cli/` 에 직접 `CLAUDE.md` 를 써 본다. 이 실습의 목표는 좋은 문서를 쓰는 게 아니라 **짧게 쓰는 감각**을 잡는 것이다.

**1단계. 먼저 하네스 없이 시켜 본다.**

```bash
cd seed/todo-cli
python -m pytest tests -q
```

테스트가 실패한다. 여기서 에이전트에게 "이 프로젝트를 살펴보고 개선해 줘"라고만 말해 본다. 무엇을 하는지 관찰하고, **하지 않았으면 하는 행동을 목록으로 적는다.** (예: 테스트 파일을 고친다, 결함을 마음대로 수정한다, 파일 구조를 바꾼다)

**2단계. 적은 목록을 `CLAUDE.md` 로 옮긴다.**

`seed/todo-cli/CLAUDE.md` 를 만들고, 1단계에서 실제로 겪은 것만 적는다. 겪지 않은 일반론은 적지 않는다. 10줄을 넘기지 않는다. 뼈대는 이렇게 잡는다.

- 이 코드가 무엇인지 한 줄
- 테스트 실행 명령
- 하지 말아야 할 것 (1단계 관찰 결과)
- 코드를 읽어서는 알 수 없는 사실

**3단계. `/context` 로 확인한다.**

`seed/todo-cli` 에서 세션을 열고 `/context` 를 실행해, 루트 `CLAUDE.md` 와 방금 만든 파일이 **둘 다** 로드되는지 본다. 이어붙임을 눈으로 확인하는 단계다.

**4단계. 경로 스코프 규칙으로 쪼갠다.**

테스트 파일에만 해당하는 규칙이 있다면 `.claude/rules/tests.md` 로 옮긴다.

```markdown
---
paths:
  - "seed/todo-cli/tests/**/*.py"
---
이 디렉터리의 테스트는 실습 과제의 사양이다. 테스트를 고쳐서 통과시키지 않는다.
```

이제 `CLAUDE.md` 에서 해당 줄을 지우고, 테스트 파일을 건드릴 때만 규칙이 로드되는지 확인한다.

**5단계. 스킬로 한 단계 더 내린다.**

가끔만 필요한 절차(예: 새 하위 명령을 추가하는 방법)를 `.claude/skills/add-command/SKILL.md` 로 옮긴다. `description` 첫 문장에 언제 쓰는 스킬인지를 반드시 쓴다.

**6단계. 다시 1단계를 반복한다.**

같은 프롬프트를 새 세션에서 다시 준다. 1단계에서 적은 "하지 않았으면 하는 행동" 중 몇 개가 사라졌는지 센다. **사라지지 않은 항목이 4장에서 훅으로 내릴 후보다.**

## ✅ 자가 점검

- [ ] 가이드와 센서의 차이를 시점(전/후)과 성격(피드포워드/피드백)으로 설명할 수 있다
- [ ] 여러 `CLAUDE.md` 가 덮어쓰기가 아니라 이어붙임으로 로드된다는 것을 알고, `/context` 로 확인할 수 있다
- [ ] `@경로` import 가 컨텍스트를 아껴 주지 않는 이유를 말할 수 있고, 최대 홉 수를 안다
- [ ] **로드 시점**(항상 / 경로별 / 호출 시)으로 규칙을 어디에 둘지 정할 수 있고, `CLAUDE.md` 권장 상한을 안다
- [ ] 스킬의 점진적 공개를 설명할 수 있고, 문서로 적는 것과 `tools`·훅으로 강제하는 것의 차이를 구분할 수 있다
